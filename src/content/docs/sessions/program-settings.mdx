## Overview

Open **Program → Settings**. This page is the vocabulary of your program: anything you define here shows up as a dropdown on the submission form, a filter on the sessions list, and a color on the agenda. Fill it in before the form goes live — adding a format after fifty submissions means fifty sessions with a blank.

![The Program Settings overview with its groups — Program structure, Schedule & venue, Review & workflow, Content](/images/kb/program-settings.png)

The overview groups the settings into tiles; the rail on the left opens each one, in this order: **Overview**, **Agenda**, **Personas**, **Rooms**, **Tracks**, **Tags**, **Levels**, **Formats**, **Languages**, **Files**, **Roles**, **Statuses**. **Personas** and **Tags** open their pages under **Settings → Library**; every other entry is a tab on this page with its own URL, so you can link a teammate straight to it.

| Group | Settings |
| --- | --- |
| **Program structure** | [Tracks](#tracks), [Levels](#levels), [Formats](#formats), [Languages](#languages) |
| **Schedule & venue** | [Agenda](#agenda), [Rooms](#rooms) |
| **Review & workflow** | [Statuses](#statuses), [Roles](#roles), [Personas](#personas) |
| **Content** | [Files](#files), [Tags](#tags) |

<Note>
Rooms, Track, Level, Format, and Language are single-select fields on a session. Tags is multi-select.
</Note>

Tracks, levels, formats, languages, and rooms all work the same way: a table with **Name** and **Uses** (how many sessions carry the value), a search box, an **Add** button, and an **Actions** menu (⋯) on each row to **Edit** or **Delete**. Deleting a value that sessions still use warns you first. **Add** opens a short menu: **Add Track** (or Level, Format, Language, Room) creates one, and **Copy from…** pulls the list from another event in your organization instead of retyping it.

## Agenda

Defaults for the agenda views — the same settings the [agenda](/sessions/agenda) reads when you schedule.

![The Agenda settings with time settings, agenda content, program statuses, format durations, and room visibility](/images/kb/program-settings-agenda.png)

| Setting | What it does |
| --- | --- |
| **Time Settings** | **Day Start Time** and **Day End Time** are the earliest and latest times shown on the agenda each day. **Interval** is the step used when you drag to create or resize a session. |
| **Agenda content** | Whether the agenda shows **Sessions (non-abstract program items)**, **Abstracts**, or **Both sessions and abstracts**. |
| **Program Statuses** | Which statuses appear on the public agenda. Typically Accepted, sometimes Accept Queue and Pending while the program is taking shape. |
| **Program Format Durations** | A default duration per format — a 20-minute lightning talk, a 90-minute workshop — so a dragged session lands at the right length. |
| **Room Visibility** | **Show all rooms** or **Select individual rooms** for the public agenda. |
| **Add to Calendar** | The title, location, and description sessions carry into a speaker's or attendee's calendar, built from session merge tags. **Preview as…** shows the result for a real session. |
| **Subsessions** | **Participants shown on the parent session** decides which subsession participants also appear on the parent: **All participants (default)**, **Presenting author only**, or **None**. The create-subsession panel starts from this setting and lets you override it each time. |
| **Participant Inventory** | **Enable participant inventory** to set minimum and maximum participant targets per session and track assignment status on the Sessions grid. Off by default; the panel appears once Sessionboard support has enabled the feature for the event. See [Track participant inventory on sessions](/sessions/participant-inventory). |

Click **Save Changes** when you're done; the agenda picks the new defaults up immediately.

## Tracks

Broad themes attendees filter by — “Facilitation and Programming”, “Industry and Business”, “Post-Conference”. Each track has a color, and that color is what the agenda and [embeds](/sessions/embeds) paint session cards with when colored by track.

![The Tracks table with each track's color, name, and how many sessions use it](/images/kb/program-settings-tracks.png)

## Levels

The expertise a session expects of its audience — “Beginner”, “Intermediate”, “Advanced”.

## Formats

The shape of the session — “Keynote”, “Workshop”, “Panel”, “Poster”. Give each format a default duration under [Agenda → Program Format Durations](#agenda) and dragged sessions land at the right length.

## Languages

The language a session is delivered in — “English”, “Spanish”, “French”. Unrelated to the language the portal is shown in; that is [portal translation](/settings/language-translation-variant).

## Rooms

The physical rooms or virtual locations sessions can be scheduled into.

- **Name** — “Ballroom A”, “Exhibit Floor 1”, “Main Stage”.
- **Capacity** — the most people the room holds, up to 100,000. Shown in the agenda's Rooms view, not in embeds.
- **Display Order** — how rooms are arranged left to right in the [agenda embed](/sessions/embeds), lowest first. Rooms with the same order value fall back to alphabetical.

## Statuses

**Program Statuses** are the workflow a session moves through. The standard statuses — **Pending**, **Accept Queue**, **Accepted**, **Decline Queue**, **Declined** — can be reordered but not renamed: open one and only **Display Order** is editable. If your committee thinks in stages like “Shortlisted” or “Needs Revision”, add a custom status.

![The Program Statuses table with the default statuses and their categories, portal names, and uses](/images/kb/program-settings-statuses.png)

<Steps>
  <Step title="Add Status">
    Click **Add** above the table, then **Add Status**. (**Copy from…** on the same menu brings the custom statuses over from another event.)
  </Step>
  <Step title="Name and categorize it">
    - **Name** — what your team sees, for example “Pending Review”.
    - **Category** — every status maps onto one of the five standard statuses and behaves like it. A custom status in the **Accepted** category syncs to integrations, shows on the agenda, and opens portal tasks exactly as Accepted does.
    - **Color** and **Display Order** — how the status looks and where it sits in dropdowns.
    - **Show custom status name to external users** — whether submitters see your name (“Shortlisted”) or the category label (“Pending”) in the portal. The **Portal Name** column shows what they'll get.
  </Step>
  <Step title="Create">
    Click **Create**. The status is available in the **Status** field on every session and as a form's **Default status for new submissions** under [Form Settings](/sessions/submission-forms#new-submissions).
  </Step>
</Steps>

Custom statuses are archived rather than deleted. **Archive** asks which status to move existing sessions to (**Replace with status**), so nothing is left without one; submission forms that defaulted to the archived status fall back to Pending.

**Participant Statuses** on the same page are the speaker-acceptance statuses — the answer a participant gives when asked to confirm. They map onto **Pending**, **Accepted**, or **Declined** in the same way, so a custom “Backup Speaker” status can behave as Accepted.

## Roles

Roles are the parts people play on a session. Sessionboard starts with three — **Speaker**, **Chairperson**, **Moderator** — and each maps to a **Category** that decides how the role is represented in integrations and [embeds](/sessions/embeds).

![The Roles table with each role's category, participant count, and Manage toggle](/images/kb/program-settings-roles.png)

- **Participants** — how many people currently hold the role.
- **Manage** — **On** gives the role its own page under **CRM**, alongside Speakers.

The **Actions** menu (⋯) renames a role to your own terminology. **Add → Add Role** creates a new one:

| Field | What to enter |
| --- | --- |
| **Role Name** | A **Singular** and **Plural** form — “Co-author” / “Co-authors”. |
| **Category** | Speaker, Chairperson, or Moderator. |
| **Role Icon** | The icon shown next to the role. |
| **Display order** | Where the role sits in the Participants tab and on the form. |
| **Manage in Contacts** | Whether the role gets its own CRM page. |

New roles have portal access, so people you add in a new role can sign in to the portal for their session and are tracked as active portal users (the hint next to **Add** says so). Reach out to support if you need a role without portal access.

Deleting a role asks where to **Reassign participants to**, so nobody is dropped from a session.

<Tip>
Roles here are what the submission form offers under [Participant roles](/sessions/submission-forms#participant-information), and what the session editor's Participants tab is organized by. Submitters can add people only in the roles a form ticks under Participant roles; any role left unticked — Chairperson and Moderator on most forms — is assigned by your team on the session. These are *participant* roles, not team permissions; see [participant roles vs team roles](/concepts/participant-roles#participant-roles-vs-team-roles).
</Tip>

## Personas

Personas are AI evaluators that review sessions from a chosen perspective — a technical expert, a first-time attendee, an executive. Assign them to an [evaluation plan](/evaluations/evaluation-plans) and each one scores every submission with feedback in its own voice, which gives your human reviewers a comparison point.

Three **Default Personas** are provided and can't be edited. **Add Persona** creates your own:

| Field | What to enter |
| --- | --- |
| **Name** *(required)* | The persona's name. |
| **Role** *(required)* | Their professional role or perspective — “Thought Leader”, “Practice Manager”. |
| **Biography** | Background and expertise, which gives their feedback context. |
| **Feedback Style** | **Positive**, **Neutral**, **Constructive** (specific, actionable guidance), or **Critical** (names shortcomings without necessarily saying how to fix them). |
| **Likes** / **Dislikes** | Up to three qualities each — “Data-backed insights”, “Generic content”. |

<Tip>
Write a persona the way you would brief a reviewer: say what a good session looks like to them, give an example of what they'd praise and what they'd flag, and point them at your event's page from [Event Details](/events/event-details) for context. Then read the first few reviews and adjust.
</Tip>

**Delete Persona** on a custom persona's card removes it from every evaluation plan and deletes its reviews and scores from reporting and the session **Reviews** tab, so they no longer change averages. This can't be undone. Removing a persona from a single evaluation round is different — completed reviews stay on the submission.

## Files

Settings for the files speakers upload to their sessions through the portal: **Enable File Upload**, a **File Due Date**, a **File Limit** per session, **Enable Comments**, **Allowed File Types**, and **File Size Limits**. The whole flow — enabling uploads, what speakers see, versions and comments — is in [Enable upload and download of session content](/sessions/enable-upload-download-content).

File questions on a submission form are separate: they use **Customize question → Maximum file size** and don't inherit these settings.

## Tags

Loose keywords for anything the other fields don't cover — “Sponsored”, “Live-Streamed”, “On-Demand”. A session can carry several. Each tag can have a color, and the chip shows that color everywhere tags appear; choose **No color** for a neutral chip. On the agenda, coloring by tags keeps cards white and shows each tag as a small square — see [card colors](/sessions/agenda#card-colors). Tags are managed in the event's tag library, which the **Tags** link on this page opens.
