Approvals controls when a session file leaves Sessionboard. It does two things, and you can use either one or both:

- **Approval.** A new session file, or a new version of one, starts as **Pending**. It goes only to the reviewers you choose, one step after another, and is released once the last step approves it.
- **Release time.** Files are held back until a date and time you set, or until each file's session starts, even after they are approved. Use it for press embargoes, abstracts that can't be public before they are presented, or sponsor content that launches at a set moment.

Approvals can also keep files away from your **reviewers** until they are approved, and review the files people upload in **submission forms**, such as abstract videos. See [Hold files from reviewers](#hold-files-from-reviewers) and [Review files from submission forms](#review-files-from-submission-forms).

A file goes out only when **both** are satisfied: it is approved (or doesn't need approval), **and** its release time has passed. Until then it is not sent to integrations, embeds, galleries, the Public API or the attendee app. Every decision and every change to a release time is kept in the history.

<Note>
Approvals is an Early Access **Beta**. Request it per event from [Early Access](/get-started/early-access) and our team will switch it on for you. Once it is on, **Publish → Approvals** appears in the event sidebar and **Program → Settings → Files** gains the approval setting. In the settings and the workflow builder, a session file is called a **submission file**, and the people on a submission are its **participants**.
</Note>

## Why use it

Decks and posters often need a sign-off before they go anywhere public: a track chair checks the content, compliance checks a sponsored session, the AV team checks the format. And some files must not be public before a set moment, however ready they are: research under a press embargo, a keynote announcement, results presented at a late-breaking session. Approvals puts the sign-off and the release time on the file itself, instead of an email thread and a calendar reminder. Reviewers get an email and an in-app notification when a file is waiting on them, everyone can see who still needs to review and when each file goes out, and nothing leaves Sessionboard early by accident.

## What is held, and where

| | Approval | Release time |
| --- | --- | --- |
| **Which files** | New files and new versions uploaded after you turn approval on, that the workflow applies to | **Every** session file the workflow applies to, including files uploaded before approvals was turned on |
| **Holding slides** | Not held | Never held |
| **Applies when Require approval is off** | No | **Yes** — the release time holds on its own |

While a file is held:

- It is **not sent** to integrations, embeds, poster and content galleries, the Public API or the attendee app.
- **The Public API** still lists the file, with `url` set to `null`, `approval_status` set to `pending`, `denied` or `embargoed`, and `embargo_until` set to its release time (`null` while it waits for its session to be scheduled). Anything built on the API can show that a file exists without being able to publish it.
- **Admins still see it** on the session, on **Program → Submissions → Submission files**, and on **Publish → Approvals**, and can open and download it.
- **The speaker who uploaded it** still sees it in the portal, with its approval status.

When a new version of an approved file is waiting for review, the approved version keeps being used. A release time holds every version of a file the same way.

## Set up the workflow

![The Require approval for submission files setting on Program Settings → Files, switched on, showing a release time held until Tue, Nov 10, 2026 at 9 AM MST and an Edit approval workflow button](/images/kb/file-approvals-setting.png)

<Steps>

<Step title="Turn on approval for session files">

Go to **Program → Settings → Files** and switch on **Require approval for submission files**. The first time, this opens the workflow builder, **Submission files approval workflow**. Afterwards, use **Edit approval workflow** here, or **Edit workflow** on the **Workflows** tab of **Publish → Approvals**.

![The Session files and Form files cards on the Workflows tab, both on. Session files shows 2 steps, 4 files in review now, Hidden from reviewers until approved Off, a release time held until Tue, Nov 10, 2026 at 9 AM MST and 9 files held by it. Form files shows 1 step and Hidden from reviewers until approved On](/images/kb/file-approvals-workflow-card.png)

</Step>

<Step title="Choose which files the workflow applies to">

**Applies to** is **Every new submission file.** by default. **Limit to some files** narrows it with conditions, for example only files in the Poster upload slot, or only files on sessions in the Late-breaking track. The same conditions decide which files need approval and which files the release time holds.

![The top of the Submission files approval workflow builder, with the Require approval switch on, Hold files from reviewers until approved, Flag videos longer than (minutes), and Applies to set to Every new submission file with Limit to some files and Filter by a submission field](/images/kb/file-approvals-builder-top.png)

</Step>

<Step title="Add steps">

Steps run one after another. Reviewers inside a step work in parallel. For each step:

| Setting | What it does |
| --- | --- |
| **Only run this step when…** | Optional conditions. A step whose conditions don't match the file is skipped and recorded in the history. |
| **Who reviews** | People or roles from your event team, with optional **Route to** rules (see below). |
| **Approval needed from** | **Any one** reviewer, **Everyone**, or **At least N**. |
| **Due within (hours)** | How long reviewers have for this step. |

![A workflow step named Track review with no step condition, a Route to rule that sends files whose File format is Video to Isaias Murazik under the label Videos, Otherwise route to Jaren Connelly, Approval needed from Any one, Due within 48 hours](/images/kb/file-approvals-steps.png)

</Step>

<Step title="Set a release time (optional)">

Leave **Release time** on **As soon as approved** for no embargo, or hold files until a set time. See [Hold files until a release time](#hold-files-until-a-release-time).

</Step>

<Step title="Set new versions and reminders">

**On a new version, restart from** decides whether a replaced file goes back to **The first step** or **The step it was on**. **Automatic reminders** nudges reviewers who haven't decided every so many hours, up to the number of times you set. Leave it empty for no automatic reminders.

</Step>

<Step title="Test the routing, then save">

Pick an existing file in the test panel to see which steps would run for it and who would review each one, then **Save workflow**.

</Step>

</Steps>

Reviewers must be active members of the event team, so everyone you assign can open the review. Roles that are not on the event team, such as **Portal User** and the evaluator roles, are not offered as reviewers. Saving changes while files are mid-review doesn't re-route them: the new steps and reviewers apply from their next step.

**Save workflow** refuses a workflow that could leave a file with nobody to review it, and names the step:

- a **Route to** rule or **Otherwise route to** that reaches nobody on the event team, for example a role with no members;
- **At least N** where N is more than the people a route can reach. Each file goes to one route, so N must fit the smallest one.

A workflow that is switched off can always be saved, so you can turn off a broken one. The test panel shows the same warning on any step that would reach nobody.

If a file still lands on a step with nobody to review it, for example because everyone was removed from the role after you saved, the file stays **Pending**, the review says so, and the event's admins and whoever last saved the workflow get an email and an in-app notification. Add a reviewer to the step, or use **Override**.

Cloning the event copies the workflow along with its submission forms; see [Clone an event](/faq/clone-an-event#what-gets-copied) for what carries over.

## Route files to the right reviewers

A **Route to** rule sends matching files to different reviewers, for example the Retail track to its chair, or posters to the poster committee. Rules are checked in order and the first matching rule wins. Files that match no rule go to the step's **Otherwise route to** reviewers. A route can have a label, such as *Posters*, that reviewers see on the file.

Conditions, for steps, routes and **Applies to**, can check the file's **File type**, **Upload slot**, **File format** (PDF, Office document, image, video, audio), and **Uploaded by** (speaker or participant, event team, or API / integration), and the session's **Track**, **Format**, **Level** and **Sponsor tier**.

**Filter by a submission field** adds conditions on a submission field, with the same operators the Submissions list offers for that field type (number fields get the comparison operators too). It lists the fields an approval workflow can check: every custom submission field (text, number, date, tree, dropdown and the rest), plus the standard **Track**, **Format**, **Level**, **Language**, **Tags**, **Status**, **Title**, **Description**, **Starts At**, **Ends At**, **Capacity** and **CEU Credits** fields, under the names your event gives them. Other standard fields, such as **Speakers**, **Location** and **Owner**, aren't offered, because a workflow can't evaluate them. All the field rows you add must match, and together they count as one condition beside the others under the **Match** all/any selector. The routing test panel previews them too. Field filters are checked when a file is uploaded.

<Note>
**A release time can't be combined with submission field conditions in Applies to.** Saving a workflow that has both is refused with the message *A release-time embargo cannot be combined with submission field conditions in “Applies to” yet. Remove the submission field conditions, or turn the embargo off.* Narrow **Applies to** with the file and session conditions above instead (such as **Upload slot** or **Track**), or set **Release time** to **As soon as approved**. Submission field conditions on steps and routes are not affected.
</Note>

**Uploaded by** follows where the file was uploaded, not who uploaded it: a file uploaded in the speaker portal counts as **Speaker / participant** even when a team member uploads it there as a speaker, and a file uploaded on the session's **Files** tab counts as **Event team**.

Use the test panel before you save: it shows, for a real file, which steps run and who reviews each one.

## Hold files until a release time

**Release time** in the workflow builder holds files back until a set time, even after they are approved. Choose one:

- **As soon as approved** — no embargo. Files go out once the last step approves them.
- **At a date and time** — every file waits for one release time, for example a press embargo.
- **When each file's submission starts** — each file waits for its own session (submission), with an optional offset.

A release time can't be saved while **Applies to** uses **Filter by a submission field**; see [Route files to the right reviewers](#route-files-to-the-right-reviewers).

![The Release time section set to At a date and time of Nov 10, 2026 at 9 AM in America/Los Angeles, the event time zone, previewed as 12 PM EST in the viewer's time and 5 PM UTC, a note that the release time holds every session file the workflow applies to, and the release time change history](/images/kb/file-approvals-release-time.png)

<Warning>
**Set the release time before files start syncing.** If a file an integration already received is held again later (reverted to pending, denied, put under a later release time or an extra hold, or Approvals switched on), it is removed at that integration's next sync: deleted from the session in **Cvent**, **Bizzabo**, **ASP**, **Grip** and **Swoogo**, and unlinked from the session in **Swapcard**. Copies made outside Sessionboard (downloads, files the other system already published) can't be recalled.
</Warning>

### Release at a date and time

Pick a **Date**, a **Time** and a **Time zone**. The time zone defaults to the event's time zone, and you can search for any other. The preview underneath shows the exact release moment three ways: in the zone you chose, in your own time zone, and in UTC. Check it before you save, especially when the embargo was given to you in another zone.

Daylight saving time is handled for you:

- **A time that doesn't exist** — inside the hour the clocks skip in spring — can't be saved. Choose a time outside it.
- **A time that happens twice** — inside the hour the clocks repeat in autumn — releases at the **later** of the two, so files are never released early. The preview says so.

The release time can't be in the past when you set it. Once it passes, files are released and the release time stays on the workflow as a record.

### Release when each submission starts

Each file waits for its own session's scheduled start, moved by an offset of up to 7 days **before** or **after** it, in minutes, hours or days. For example, *1 hour before each file's session starts* lets attendees open the deck in the app just ahead of the talk.

![The When each file's submission starts options set to 1 hours before the submission starts, with the summary 1 hour before each file's submission starts and a note that rescheduling a submission moves its release](/images/kb/file-approvals-release-session-start.png)

- **Rescheduling a session moves its release.** The release time is always read from the session's current start.
- **Files on a session with no start time stay held** until the session is scheduled; their badge reads **Embargoed · submission not scheduled**. This is the opposite of a [content gallery's](/site/content-galleries) own embargo, where items without a start time are never embargoed: here, an unscheduled session never releases a file by accident.

### Hold one file longer

A single file can be held past the workflow's release time, for example one abstract under a journal embargo that lifts two days after the session. Open the file from **Publish → Approvals**, and in **Release** choose **Hold this file longer**. Pick the date, time and time zone (the event's zone by default) and **Hold file**.

![The Release panel in the review drawer, showing the file is held until Thu, Nov 12, 2026 at 9 AM MST, the workflow release is Tue, Nov 10, 2026 at 9 AM MST, and the extra hold was set by Alicia Carter, with Remove extra hold and Change extra hold](/images/kb/file-approvals-release-panel.png)

- **An extra hold can only make the release later, never sooner.** A time earlier than the workflow's release is refused.
- **It holds every version of the file**, including versions uploaded afterwards.
- **Reviewers of the file can add or extend an extra hold.** Only admins who manage session files can move one earlier or **Remove extra hold**, because either change releases the file sooner.
- **Remove extra hold asks first when it would release the file now** — when the file is approved and the workflow's release time has passed, so only this hold keeps it back. Confirm with **Remove and release**. If the file is still held by approval or by the workflow's release time, the hold is removed without asking.
- Each extra hold, change and removal is recorded in the file's history, with who made it and the old and new times.

![The Hold this file longer form with the date Nov 13, 2026, the time 9 AM and the time zone America/Los Angeles (GMT minus 8), the event time zone, with Cancel and Hold file](/images/kb/file-approvals-hold-longer.png)

### Changes that release files sooner

Changing the release time to an earlier one, switching to **As soon as approved**, switching mode, or narrowing **Applies to** while a release time is on can release held files at once. Before saving such a change, Sessionboard tells you how many files are held right now and asks you to confirm with **Save and release**. **Keep editing** goes back without saving.

![The Release held files sooner? confirmation, saying 232 files are held by the release time right now, any file this change releases goes out as soon as you save and can't be recalled, and 2 files are mid-review, with Keep editing and Save and release](/images/kb/file-approvals-release-sooner.png)

### Changes that hold files that are live now

A release time holds **every** file the workflow applies to, including files that integrations, embeds and the Public API already have. When you set or move a release time later, or widen **Applies to** while one is set, Sessionboard counts the files that are live now and would be held, and asks you to confirm with **Save and hold**. Held files stop being sent and disappear from embeds and galleries until the release time passes. The Public API keeps listing them, with `url` set to `null` and their approval and release details, as described in [What is held, and where](#what-is-held-and-where).

Every change to the workflow's release time is listed under **Release time changes** in the builder, newest first, with who changed it, when, and the old and new values. The builder also shows how many files the release time holds right now.

### When the release time passes

Within a minute of a file's release time, Sessionboard releases it and tells your integrations, embeds and galleries that it is available. Each integration picks it up on its next sync, so allow for that sync interval when the timing matters. A file that is still pending or denied stays held after its release time passes, until it is approved.

## Review files

**Publish → Approvals** lists every file in the workflow, with tabs for **Waiting on me** and **All approvals**, and a status filter for **Pending**, **Approved** and **Denied**. The **Files** menu switches the list between **Session files** and **Form files**. Each row shows the session with its room and time, its **Session ID** (for example SESS-226, the same ID as on the Files list), the current step, the avatars of the reviewers it is still waiting on, and, in **Release**, when a held file goes out.

![The All approvals tab listing six session files, each with its Session ID (such as SESS-5), session, step, reviewers, a Pending, Denied or Approved status, and a Release column showing Embargoed until Nov 10 at 9 AM MST](/images/kb/file-approvals-queue.png)

**Review** opens the file with a preview (**Full screen** for decks and posters), its release time, the steps it has passed and the ones still to come, who has decided at each step, and its full history.

Word, PowerPoint and Excel files preview in Microsoft's Office viewer, including files still held for approval: the viewer reads the file through a signed link that expires after a few hours, never a public address. Files over the viewer's limit (10 MB for Word and PowerPoint, 5 MB for Excel) show **This file is too large to preview here. Download it to review.** with **Download**. The same preview is used in the **Files** sidebar and on submission sidebars.

- **Approve** completes your part of the step. When the step's rule is met, the next step starts. After the last step, the file is approved, and released if its release time has passed.
- **Deny** asks for changes. A note is required, and it is sent to the person who uploaded the file. The remaining reviewers don't need to act.
- **Remind** emails the reviewers who haven't decided yet. Each reviewer can be reminded once every 4 hours.

Select several rows to approve, deny or remind in bulk. Before **Approve** or **Deny** goes ahead, Sessionboard says how many files it will change, for example *Approve 37 of 200 selected — 163 are not waiting on you*. Only the files waiting on you are decided. Event team members whose role is limited to some sessions see only the files on those sessions, plus any file they have been asked to review.

### Override a decision

Admins who can edit session files can **Override** from the review. The menu offers only the moves that change the file's status:

- **Approve now** skips any remaining steps. Shown unless the file is already approved.
- **Deny now** sends the file back with a note. Shown unless the file is already denied.
- **Revert to pending** puts an approved or denied file back to **Pending** and restarts the workflow from the first step. It is not offered on a file that is already pending.

Overrides are recorded in the history as overrides. **Approve now** does not lift a release time: an approved file still waits for it.

## On the Files list

**Program → Submissions → Submission files** shows each file's approval status and, for a held file, when it is released. Filter by **Waiting on me**, **Pending**, **Approved**, **Denied** or **Embargoed**: the Embargoed tab lists every file the release time is holding right now, approved or not. The list also shows the session's room and time and who last changed the file. The session's **Files** tab shows the approval status on each file.

![The Embargoed tab of the Files list with 232 files, where each row shows its status, such as Denied or Pending · Track review, above a badge reading Embargoed until Nov 10, 2026, 9 AM PST](/images/kb/file-approvals-files-list.png)

## Hold files from reviewers

By default, reviewers who see uploaded files on their submissions (a review plan with **Include uploaded files** on) see a file as soon as it is uploaded, approved or not. To keep files away from them until they pass review, open the workflow builder and turn on **Hold files from reviewers until approved**. It is on for a new workflow and off for a workflow saved before the setting existed.

- **Session files.** Evaluators see only approved files. While a new version of an approved file waits for review, they keep seeing the approved one.
- **Form files.** Evaluators see an empty field until the file is approved. A denied file is never shown to them.

The hold covers every place an evaluator reads a submission: the submission's fields and **Uploaded files**, related sessions, the round list and its search and filters, public voting, the legacy **My Evaluations** page, and the submission an AI evaluator is given. Evaluators are told a file was uploaded once it is approved, not before. Admins still see every file on the session and on **Publish → Approvals**.

In the review drawer and the queue, a held file shows **Hidden from reviewers**. The workflow card on the **Workflows** tab shows **Hidden from reviewers until approved** as **On** or **Off**.

<Note>
The hold applies to evaluation plans in the event. Interest form evaluation plans in the Speaker CRM and awards reviewers are not covered.
</Note>

## Review files from submission forms

Files and videos people upload in a submission form's file fields (for example, an abstract video) can have their own review, separate from the submission's status: a video can be waiting for approval while its abstract is already being scored.

<Steps>

<Step title="Set up the Form files workflow">

Go to **Publish → Approvals → Workflows**. Next to the **Session files** card, the **Form files** card covers files uploaded in submission forms. Click **Set up workflow**. The **Form files review workflow** builder has the same steps, reviewers, **Approval needed from**, due times, new-version rule and reminders as the session files workflow. **Applies to** is every new file in a submission form; **Limit to some files** narrows it. Release times and the routing test apply to session files only, so the form files builder does not show them.

</Step>

<Step title="Choose what evaluators see">

Leave **Hold files from reviewers until approved** on so reviewers see an empty field until a file is approved. Turn it off and evaluators see form files as they are uploaded, while your team still reviews them.

![The Form files review workflow panel with Require approval switched on, Hold files from reviewers until approved switched on, Flag videos longer than (minutes) set to No limit, and Applies to every new file in a submission form](/images/kb/file-approvals-form-files-builder.png)

</Step>

<Step title="Flag long videos (optional)">

Enter a number of minutes in **Flag videos longer than (minutes)**, from 1 to 600, or leave it empty for no limit. See [Flag long videos](#flag-long-videos).

</Step>

</Steps>

Conditions for steps, routes and **Applies to** can check the **Form field**, the **File format**, **Uploaded by**, **Video length**, and the session's **Session track**, **Session format**, **Session level** and **Session sponsor tier**.

A file enters review when it is saved in a form field, from the submission form, the session page, an import or the Public API. Saving the same file again does nothing. Replacing it with a different file starts the review again, from the step chosen under **On a new version, restart from**.

To follow one submission, open the session's **Files** tab: **Form files in review** lists its form files with their status, length and whether they are hidden from evaluators, and **Review** opens the same drawer as the queue.

### Flag long videos

When **Flag videos longer than (minutes)** is set, Sessionboard measures each uploaded video and shows its length on the review card and in the queue, for example **10:12 · over 8 min** when it is longer than the limit. While it measures, the card shows **Measuring length**. A video that can't be measured shows **Length not measured**.

To send long videos to someone else, add a **Video length** condition to a step or a route: **Longer than the limit**, **Within the limit** or **Not measured**. A workflow that uses it waits until the video is measured before its first step starts (the drawer says **Measuring the video. Review starts once its length is known.**). If the video can't be measured, review goes ahead with the length treated as **Not measured**.

### Moderate a file

The review drawer's **Moderate this file** section works for session files and form files:

- **Comment** adds a note to the file's history with **Add comment**. Your team sees it; the person who uploaded the file does not. Reviewers of the file and admins who can edit session files can comment.
- **Upload new version** puts a corrected file in its place and starts review again. For a session file it adds the next version, as uploading on the session's **Files** tab would. For a form file it replaces the file in the submission's form field. Only admins who can edit session files see it.

To download the file, use the preview. To ask the uploader for changes, use **Deny** with a note.

## What speakers see

In the portal, speakers see **Pending review**, **Approved** or **Changes requested** on each file they uploaded, never the steps, the reviewers or the release time. When a file is denied they see your note, with **Upload new version** to send it back for review. The new version starts the workflow again from the step you chose.

## Notifications

| When | Who | How |
| --- | --- | --- |
| A step starts, or a reviewer is added | Each reviewer on that step | Email and in-app |
| A reminder is sent, by hand or automatically | Reviewers who haven't decided | Email and in-app |
| The last step approves the file | The person who uploaded it | Email and in-app |
| A reviewer denies the file | The person who uploaded it | Email and in-app, with the note |

The emails are listed under System Notifications, in the Files & Exports category, where you can edit their wording. No email is sent when a release time passes.

## Turning it off

- **Switching off Require approval for submission files** (on **Program → Settings → Files**, then **Save Changes**) stops holding files for review, **including files that are mid-review or denied**. When any are waiting, Sessionboard says how many before it saves. Once saved, they are released to integrations, embeds, galleries and the Public API like any approved file. Switching approval back on holds them again, and integrations remove them at their next sync, but copies made in the meantime can't be recalled. Their review history is kept, and they show as **Pending · approval off** while approval is off. **A release time keeps holding files.** To lift it, set **Release time** to **As soon as approved**.
- **If the Approvals Beta is switched off for the event**, files are no longer held for review, but **a release time still holds files** so that nothing under an embargo is released by accident. Set **Release time** to **As soon as approved** before you ask for the Beta to be switched off, or contact Support to lift it afterwards.
