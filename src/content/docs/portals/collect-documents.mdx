A file request is a task that needs an upload: a signed speaker agreement, a sponsor ad, a commercial video. It works like any other [task](/portals/assign-tasks) — create it in the library, assign it to a portal, track it as a column — with a review step on top: every upload waits for you to approve or deny it, and the person can upload a new version if you send it back.

Files come up in three places, and they do different jobs. Under Program, Portals, Files is what you hand out: the programme PDF, the exhibitor manual, a venue map, or a link to a page somewhere else. Each one downloads from the portal home. <Note>
**Headshots and presentation files have better homes.** Collect headshots with the **Headshot** field on a [portal form](/portals/create-assign-forms), so the image lands on the contact record. Collect slides and handouts as [session files](/sessions/enable-upload-download-content), so you can download a whole program's decks as one zip.
</Note>

## Create a file request

<Steps>
<Step title="Open the File Requests library">
Go to **Program → Portals → File Requests** and click **Add → Add File Request**. The tabs — **All Requests**, **Contact Requests**, **Group Requests**, **Submission Requests** — filter by who the request is for.

![The File Requests library under Portals](/images/kb/portal-file-requests-library.png)
</Step>
<Step title="Fill in the request">
![The Add File Request panel](/images/kb/portal-file-request-add.png)

| Field | What it does |
| --- | --- |
| **Title** | The name of the task on the portal. |
| **Type** | **Contacts** (one person), **Groups** (a sponsor or exhibitor company), or **Submissions** (each session). |
| **Instructions** | What to upload and what good looks like — format, dimensions, deadline context. |
| **Include sample file(s) with this request** | Attach an example the person can download before they upload their own. |
| **Default status for new submissions** | The status every new upload starts in, including a new revision: **Pending (default)** puts it in your review queue, while **Approved** or **Denied** set it straight away. Duplicating the request keeps this setting. |

Click **Create File Request**. You can change the default later from the request's **Edit** panel; uploads already received keep their status.
</Step>
</Steps>

<Warning>
A file request accepts **one file per person**. If they need to replace it they upload a new revision, and you see the history. To collect several files at once, use a [form](/portals/create-assign-forms) with file upload questions instead. Uploads can be up to 5 GB each.
</Warning>

## Assign it to a portal

Open the **⋯** menu on the portal card and choose **Edit Tasks**. In the **File Requests** section of the **Assign Items** step click **Add**, tick the request, and click **Add Selected**. Then use the pencil under **Actions** to set its **Alias**, **Due Date**, **Extended Due Date**, **Required**, **Make Completed Tasks View-Only** and — for Submissions requests — **Assign By Filter**. These settings are the same as for a task; see [Create & assign tasks](/portals/assign-tasks#assign-the-task-to-a-portal).

![Edit Settings for an item on a portal](/images/kb/portal-item-settings.png)

A file request can also go to a few people without a portal: select them in **Contacts**, then **Assign → File Requests** — see [Assign tasks (including bulk)](/portals/task-assignment).

## What the person sees

On the portal the request is a task with an upload. After they upload, the task reads **Submitted - Pending Feedback** until you act on it. If you deny it, it reads **Denied** and they can upload a new revision; if you approve it, it is **Completed**.

<Warning>
Denying a file does **not** email the person. Send them a message from the submission (below) so they know what to change.
</Warning>

## Review and approve

<Steps>
<Step title="Open the results">
On **Program → Portals → File Requests**, open the request's **⋯** menu and choose **View Submissions**. The **Results** table lists everyone who has uploaded, with the file, status and date.
</Step>
<Step title="Open a submission">
Click a row to open **Submission Details**. The **Details** tab shows who submitted, when, the **Criteria** you wrote, and the **Revision History** — every version they have uploaded, newest marked **Current**.
</Step>
<Step title="Approve, deny, or revert">
Use **Approve** or **Deny** on the current revision. Made a mistake? **Revert to Pending** puts it back in the queue. You can also click **Add Revision** to upload a file on the person's behalf.
</Step>
</Steps>

## See who has finished

The request is a column in **Contacts**, **Speakers**, **Sponsors** or **Exhibitors** — add it with **Columns** and save the view ([Dashboard views](/reporting/dashboard-views)).

| Icon | Status | Meaning |
| --- | --- | --- |
| Green file-check | **Approved** | Reviewed and accepted. |
| Yellow clock | **Pending Approval** | Uploaded, waiting for you. |
| Red file-x | **Rejected** | Denied; the person can upload a new revision. |
| Blue file-clock | **Assigned Via Portal** | Reached them through a portal; nothing uploaded yet. |
| Amber clipboard | **Manually Assigned** | Assigned to this record directly; nothing uploaded yet. |
| Grey file-question | **Not Assigned** | Click to assign to this one record. |

## Get notified when a file comes in

Each upload (and each new revision) can reach the event team as a bell notification and an email with the subject `<Contact Name> submitted a file for "<Task Name>" in <Event Name>`. The person who uploaded is never notified about their own upload.

**File Request Submitted** starts **off**, because a busy request can mean one email per upload. To turn it on for yourself, open **Notifications → Preferences** and switch on the in-app and/or email column for **File Request Submitted**. Preferences are per person; if you would rather have one digest a day, set **Email frequency** to **Daily summary** on the same page. See [Notifications](/communications/notifications).

## Download the files

On the **Results** page, **Download All Files** builds a bundle of the current revision from every submission; choose **Group files by** to decide how the zip is organised. **Download bundle (with other sources)...** adds files collected through forms and sessions to the same export. For one file, open the submission and click **View File** or **Download File**.

The **⋯** menu on the same page has **Export Comments** and **Export .CSV / .XLSX** for the table itself.

## Messages on a file request

Each submission has a **Messages** tab. Anything your team writes there emails the person (`<Admin Name> sent a message about "<Task Name>" in <Event Name>`); anything they write back emails every admin on the event with **Document request comment** switched on under **Notifications → Preferences**. Messaging has to be enabled on the portal — **Configuration → Enable messaging** — for them to reply; see [Portals 101](/portals/portals-101#configuration).
