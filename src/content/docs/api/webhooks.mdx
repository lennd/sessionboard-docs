Webhooks send your application an HTTP `POST` the moment something changes in Sessionboard, so you do not have to poll the API. Each request is signed, retried on failure, and recorded in a delivery log you can inspect and replay.

## Event-level and organization-level endpoints

You can add endpoints in two places:

- **An event:** **Settings › Integrations › Webhooks** in that event. The endpoint receives changes in that event only.
- **The organization:** **Organization Settings › Webhooks**. The endpoint receives changes in every event of the organization, and organization-level changes such as new contacts.

Both kinds behave the same way; only the scope differs. Interest Form, Awards and Awards Call for Reviewers events belong to the organization rather than an event, so only organization endpoints can receive them.

## Payload structure

Every delivery is a JSON body with two keys. `data` identifies the record that changed, and `metadata` describes the change. To read the record itself, call the Public API at `metadata.resource_url`.

```json
{
  "data": {
    "id": "fd4e0275-f018-40bc-909a-f8cdfa0df354",
    "sourceOfChange": "user"
  },
  "metadata": {
    "action": "session.updated",
    "actor_id": 7,
    "event_id": 4001,
    "org_id": "757e8d5b-ce66-45f5-ab36-273414f8ab2f",
    "resource_url": "https://public-api.sessionboard.com/v1/event/4001/sessions/fd4e0275-f018-40bc-909a-f8cdfa0df354",
    "version": 1,
    "datetime": "2026-04-28T16:00:00Z"
  }
}
```

| Field | Description |
| --- | --- |
| `data.id` | Identifier of the record that changed. |
| `data.sourceOfChange` | Whether a user or an agent made the change. |
| `metadata.action` | The event type, for example `session.updated`. |
| `metadata.actor_id` | ID of the user who made the change. `null` for system changes. |
| `metadata.event_id` | The Sessionboard event the change belongs to. `null` for organization-level changes. |
| `metadata.org_id` | Your organization's identifier. |
| `metadata.resource_url` | Public API URL that returns the full record. |
| `metadata.version` | Payload schema version, currently `1`. |
| `metadata.datetime` | UTC ISO 8601 time the change happened in Sessionboard. |

<Note>
  Sessionboard may add fields to `data` and `metadata` at any time, so ignore fields you do not recognize. Removing or renaming a field bumps `metadata.version`.
</Note>

## Create an endpoint

<Steps>
  <Step title="Open Webhooks">
    In the event, go to **Settings › Integrations › Webhooks**. For every event at once, go to **Organization Settings › Webhooks** instead.

    ![The Webhooks screen with one endpoint listed](/images/api/webhooks-endpoints-list.png)
  </Step>
  <Step title="Add the endpoint">
    Click **Add endpoint** and enter your receiver's URL. It must be a public `https` address; private and internal addresses are refused. Optionally add a description, choose event types, set a rate limit, and add custom headers.

    ![The Add endpoint form with the URL, description, enabled switch and event types](/images/api/webhooks-add-endpoint.png)
  </Step>
  <Step title="Copy the signing secret">
    After you save, Sessionboard shows the endpoint's signing secret (it starts with `whsec_`). Store it with your receiver to verify each request. You can reveal it again from the endpoint at any time.
  </Step>
</Steps>

Open an endpoint to see its settings, its signing secret, and the **Testing** and **Logs** tabs.

### Custom headers and rate limit

- **Custom headers** are sent with every request, for example an API key your receiver expects. Values are hidden after you save. You can add up to 20. Sessionboard sets `Content-Type`, `User-Agent` and the `svix-*` and `webhook-*` signature headers itself, so you cannot override them.
- **Rate limit** caps how many requests per second Sessionboard sends to the endpoint. Leave it empty for no limit.

## Verify the signature

Every request carries three headers. Each is sent under two names, `svix-*` and the [Standard Webhooks](https://www.standardwebhooks.com/) `webhook-*` equivalent, with identical values:

| Header | Value |
| --- | --- |
| `svix-id` / `webhook-id` | Unique message ID (`msg_…`). The same ID is sent on every retry of a message, so use it to ignore duplicates. |
| `svix-timestamp` / `webhook-timestamp` | Unix time in seconds when the request was signed. |
| `svix-signature` / `webhook-signature` | One or more space-separated signatures, each `v1,<base64>`. |

The signature is an HMAC-SHA256 of `{id}.{timestamp}.{body}`, keyed with the base64-decoded part of your secret after `whsec_`. Verify against the raw request body, before any JSON parsing. Reject requests whose timestamp is more than five minutes old.

The easiest way is a Standard Webhooks library. The `svix` and `standardwebhooks` packages both work:

<Tabs syncKey="api-code">
<TabItem label="Node.js">
```javascript
import { Webhook } from "svix";

const wh = new Webhook(process.env.SESSIONBOARD_WEBHOOK_SECRET);

app.post("/webhooks/sessionboard", express.raw({ type: "application/json" }), (req, res) => {
  try {
    const event = wh.verify(req.body, {
      "svix-id": req.header("svix-id"),
      "svix-timestamp": req.header("svix-timestamp"),
      "svix-signature": req.header("svix-signature"),
    });
    // handle event.metadata.action
    res.sendStatus(204);
  } catch {
    res.sendStatus(400);
  }
});
```

</TabItem>
<TabItem label="Python">
```python
from svix.webhooks import Webhook, WebhookVerificationError

wh = Webhook(os.environ["SESSIONBOARD_WEBHOOK_SECRET"])

@app.post("/webhooks/sessionboard")
def receive():
    try:
        event = wh.verify(request.get_data(), dict(request.headers))
    except WebhookVerificationError:
        return "", 400
    # handle event["metadata"]["action"]
    return "", 204
```
</TabItem>

### Rotating the secret

**Rotate secret** creates a new secret and signs with it immediately. For the next 24 hours each request is also signed with the old secret, as a second `v1,…` entry in the signature header, so your receiver keeps verifying while you deploy the new one. Libraries accept a request when any of its signatures matches.

## Delivery and retries

- A delivery succeeds when your endpoint answers with any `2xx` status within 15 seconds. Redirects are not followed.
- A failed delivery is retried with the same message ID on this schedule after the first attempt: 5 seconds, 5 minutes, 30 minutes, 2 hours, 5 hours, 10 hours and 10 hours. That makes eight attempts over about 28 hours.
- An endpoint whose deliveries have all failed for 5 days in a row is disabled automatically, and the change is recorded in History. Turn it back on from **Edit** once your receiver is fixed.
- Each endpoint receives one request at a time. A message waiting for a retry does not hold up newer messages, so do not rely on delivery order; use `metadata.datetime`.

## Logs, resend and recover

The **Logs** tab lists every attempt with its status, response code and duration. Open an attempt to see the payload, your receiver's response body, or why the request failed (for example a DNS or TLS error).

- **Resend** queues a message again. If a retry is already waiting, it is sent now instead of adding a copy.
- **Recover failed messages** resends every message since a time you choose that has never been delivered successfully.

Creating, editing, deleting, revealing or rotating an endpoint's secret is recorded in History.
