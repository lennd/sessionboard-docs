The Sessionboard MCP (Model Context Protocol) server lets AI assistants like Claude, ChatGPT, Microsoft Copilot, and Google Gemini query and manage your event data directly. Built on the open [Model Context Protocol](https://modelcontextprotocol.io/) standard, it exposes **39 tools** covering search, reads, natural-language queries, cited answers about an event, reports and dashboards, and write operations.

This page is the technical reference. If you just want to connect an assistant, the Help Center has friendlier step-by-step guides with screenshots — start at the [AI assistants overview](https://learn.sessionboard.com/integrations/connect-ai-assistants):

- [Connect Claude](https://learn.sessionboard.com/integrations/connect-claude) — including Sessionboard's listing in Claude's connector directory
- [Connect ChatGPT](https://learn.sessionboard.com/integrations/connect-chatgpt) — install the Sessionboard app from ChatGPT's plugin directory (US), or a developer-mode connector with your regional URL (EU / Middle East)
- [Connect Microsoft Copilot](https://learn.sessionboard.com/integrations/connect-microsoft-copilot) — via a Copilot Studio agent
- [Connect Google Gemini](https://learn.sessionboard.com/integrations/connect-google-gemini) — Gemini app, Gemini Enterprise, or the Gemini CLI

Workflows built on these tools (Agent Skills, one `SKILL.md` per job, plus a Claude Code plugin) are in the [Skills](/skills) tab.

## What is MCP?

Model Context Protocol is an open standard that enables AI assistants to securely connect to external data sources and tools. Instead of copying data into prompts, MCP lets the AI query and update your data on demand through a structured interface.

## Server URLs by region

Each Sessionboard region runs its own MCP server. Use the one matching where your organization is hosted:

| Region | MCP server URL |
| --- | --- |
| United States | `https://mcp.sessionboard.com/mcp` |
| Europe | `https://mcp-eu.sessionboard.com/mcp` |
| Middle East | `https://mcp-me.sessionboard.com/mcp` |

The server uses the streamable HTTP transport and supports OAuth 2.0 with PKCE and dynamic client registration — most clients discover the sign-in flow automatically.

## Prerequisites

<Warning>
  Two things must be true before the hosted MCP server will accept a sign-in:

  1. **AI features are enabled for the organization.** Contact Sessionboard support or your account manager if they are not.
  2. **The person signing in has the Connect AI assistants permission.** Organization administrators have it. Other roles need it granted in role settings.

  Claude, ChatGPT, Copilot, Gemini, and any other remote client connect with **OAuth**. There is no MCP switch on the organization or on an API token, and pasting an API token into the assistant will not authenticate. The hosted server (`https://mcp.sessionboard.com/mcp` and the regional hosts) accepts the OAuth bearer token from that sign-in.

  An API token is for scripts calling the public API with `x-access-token`. Those calls to `/v1/insights/...` need the **`read:insights`** scope (a token with an empty scope list is the legacy full-access case and can call them too). Write scopes such as `write:sessions` are separate.
</Warning>

## Setup

<Steps>
  <Step title="Connect your AI client">
    Most assistants (Claude, ChatGPT, Copilot Studio, Gemini) connect through their own UI — follow the [Help Center guides](https://learn.sessionboard.com/integrations/connect-ai-assistants) above. For clients configured by file (Claude Code, Cursor, and similar), add:

    ```json
    {
      "mcpServers": {
        "sessionboard": {
          "url": "https://mcp.sessionboard.com/mcp"
        }
      }
    }
    ```

    Swap in the EU or Middle East URL from the table above if that's where your organization is hosted.
  </Step>
  <Step title="Sign in">
    On first use the client walks you through Sessionboard's OAuth sign-in and organization consent automatically — no token to copy. A client that cannot complete that sign-in cannot use the hosted MCP URL. Scripts call the public API with an [API token](/api/authentication) instead.
  </Step>
  <Step title="Start querying">
    Ask your AI assistant questions about your event data in natural language. The assistant uses the MCP tools to query Sessionboard and return results.
  </Step>
</Steps>

## Available Tools (46)

The MCP server exposes 46 tools in five groups. Write operations use a `manage_*` pattern — one tool per entity with an `action` parameter to pick the operation (e.g., `action: "create"`).

All tools include [MCP annotations](https://modelcontextprotocol.io/docs/concepts/tools#tool-annotations) for safe AI behavior — read tools are marked `readOnlyHint: true`, every `manage_*` tool is marked `destructiveHint: true` because each can overwrite an existing record through its `update` action (even the ones with no `delete`), and all are `openWorldHint: false` because every tool is bounded to your organization's data. Clients such as Claude and ChatGPT use these hints to ask for confirmation before a write runs.

### Registration (9 tools)

Read-only answers about an event's registration: the funnel, conversion per form, abandoned checkouts, the waitlist, attendees, orders, payments, membership, capacity and setup. They need the `read:registrations` scope, which is in preview: tick it under **Opt-in** when you create an API token, or name it in your OAuth `scope` request. The event must have Registration turned on (Early Access); otherwise these tools say so instead of answering.

| Tool | Actions | Description |
|------|---------|-------------|
| `read_registration_summary` | — | Registrations by status, by day, per ticket type, attendee type and form; member mix; revenue; orders per status; invoices still owed; capacity pools |
| `find_registrations` | `search`, `get` | Find attendees by a name, email or company fragment, or filter by status, ticket type, attendee type or form; one registration in full |
| `read_registration_orders` | `list`, `get` | Find an order by number or buyer email, or list orders by status (`awaiting_invoice`, `partially_paid` still owe); one order in full |
| `read_registration_payments` | `list`, `get` | Payment records: card and bank payments through your payment gateway and offline money, failed attempts with their reason, refunds and the charge they refund. Never card numbers or tokens |
| `read_registration_members` | `lookup`, `list` | Check one email the way the form does (member, lapsed or none), or list registrations with the membership recorded when they registered |
| `read_registration_capacity` | — | Every ticket type's capacity, sold and available, plus shared capacity pools |
| `read_registration_funnel` | — | Conversion per registration form: form views, checkouts started and completed, registrations, the rates between them, abandoned checkouts and what they held, abandonment in the last 7 and 30 days and by ticket type |
| `read_registration_waitlist` | — | Who is waiting, as counts: per form and ticket type, the event waitlist of closed forms, open / expired / taken offers, and each form's waitlist settings |
| `read_registration_setup` | `section` | Fee groups and their promo codes, donation funds with raised and pledged totals, workshop picking rules, the badge print queue |

Try: *"How many people registered for Annual Meeting 2026 last week, and how much is still owed on invoices?"* or *"Is ada@example.org a member, and is she registered?"* or *"Which registration form converts best, and how many checkouts were abandoned this week?"*

| Tool | Actions | Scope | Description |

## Asking about an event

`ask_event` answers a question about one event the way an organizer would want it answered. The answer is grounded in the event's program (sessions, speakers, exhibitors, sponsors), session transcripts, the event's knowledge and pinned answers, and the Sessionboard Help Center, and it cites its sources with `[n]` markers listed under **Sources**. It calls [`POST /v1/event/{eventId}/ask`](/api/reference/ask/ask-a-question-about-an-event).

| Input | Required | Description |
| --- | --- | --- |
| `event_id` | Yes | The event to ask about |
| `question` | Yes | The question, in plain language (up to 500 characters) |
| `conversation_id` | No | The `conversation_id` from a previous answer, to ask a follow-up in the same thread |
| `lang` | No | Answer language as a language tag (e.g. `en`, `fr`, `pt-BR`) |

- **Scope** — needs `read:ask`. Assistants connected before this scope existed hold only the scopes they were granted; reconnect to grant it.
- **Read-only** — marked `readOnlyHint: true`. Ask never changes the event.
- **Use it for synthesis** — "which sessions cover X", "what did speakers say about Y", "how do I set up Z". For exact counts and lists, `execute_sbql` and `query_data` are faster and exact.
- **Slow** — an answer takes several seconds; the tool waits up to 90 seconds.
- **Follow-ups** — the answer ends with a `conversation_id`. Pass it back to continue the thread.
- **Refusals come back as tool errors** — Ask turned off for the event, AI features off, the per-user question limit (with the seconds to wait), the event's daily Ask budget used up, or a question Ask would not take.

## Parameter Conventions

- **Event scoping** — All event-scoped tools require `event_id` (snake_case string).
- **Action selection** — Consolidated tools use `action` to pick the operation (e.g., `action: "create"`).
- **Entity IDs** — snake_case: `session_id`, `contact_id`, `entity_id`, `draft_id`, `widget_id`, `query_id`.
- **Optimistic concurrency** — Update actions require `updated_at` (ISO 8601 timestamp from the last read). Returns `409 Conflict` if the entity was modified since.

## Result Size Safety

All results are automatically truncated to prevent context window overflow:

- **List results** — Capped at 50 items. When truncated, the response includes `truncated: true`, `total_count`, and a `hint` with guidance on pagination.
- **Query results** — Capped at 100 rows with truncation metadata.
- **SbQL queries** — `execute_sbql` and `query_data` default to a 50-row limit. Use the `limit` parameter for more.

## Actions that wait for your OK

Some Marketing and Learning actions reach people outside your team, spend money or publish something public. When an AI assistant asks for one of these through MCP, Sessionboard does not run it. It records a request and answers with a link where a person on your team approves or declines it:

```json
{
  "status": "needs_approval",
  "approval_id": "49a31154-…",
  "url": "https://app.sessionboard.com/marketing/<orgId>/approvals?id=49a31154-…",
  "message": "Waiting for your OK in Sessionboard: https://…"
}
```

- **What waits:** launching or resuming a campaign, sending invitations or content kits, sending a "Keep everyone engaged" round or offer, publishing an event page, gallery, course or on-demand library, approving ads or raising an ad budget, starting live captions, and assigning training.
- **What runs:** drafts, edits to drafts and reads. Credit is never set or granted by an assistant.
- **Approving** runs the original request as the person who approved it, with their permissions. Declining records the answer and nothing happens. The assistant sees the outcome the next time it reads the record.
- **Don't retry.** Calling the same tool again creates another request; tell the person where to approve instead.
- Every assistant action, including the approvals, is listed under **Apps › AI assistants** in Sessionboard, with who asked and what changed. An admin can pause assistant writes for the organization; while paused, write tools return `423`.

## Security

- **Org isolation** — The SbQL compiler injects `org_id` into every query from the authenticated token. Prompt injection cannot access other organizations' data.
- **Your access, not more** — The assistant reads as the person who authorized it: what their Sessionboard role allows, in that organization, through the scopes they granted. Query results are not masked; an assistant that asks for contact emails gets them. Write tools need write scopes, and only roles with **Connect AI assistants** can authorize a connection. See [privacy details in the Help Center](https://learn.sessionboard.com/integrations/connect-ai-assistants#privacy-and-pii).
- **Scoped access** — Tokens are restricted to specific scopes and optionally to specific events.
- **Audit logging** — Every API call is recorded with source, method, response time, and token ID. For `ask_event` the question text is redacted from the log.
