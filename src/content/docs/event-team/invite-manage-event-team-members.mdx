Event Team is where you give colleagues access to an event and decide how much of it they see. This guide covers:
- How to invite team members to your event
- How to view and manage permissions for default roles
- How to create custom roles
- How to control field permissions (who sees or edits which fields)
- How to limit which session statuses a role can set
- How to apply roles and field settings to many events at once

## Why use it

Event Team gives each colleague, reviewer or vendor exactly the access their job needs. Default roles cover the common cases; custom roles let you hide fields such as fees or phone numbers, scope a session manager to one track, and limit which session statuses a role can set — and from which — so your review workflow is enforced by the product rather than by reminders.

## Inviting team members

Open **Event Team** at the bottom of the event navigation. The **Team** tab lists everyone with access to this event — name, email, permission role, last login and tags — and the chips above the table filter it to **Event Admins**, **Evaluators** or **Portal Only Access**.

![The Event Team page — the Team tab with the Add button and the role filter chips](/images/kb/event-team-list.png)

Select **Add**, then **Invite User**. (**Add From…** copies people who are already on another of your organization's events — pick them, choose the permission they get on this event, and decide whether to send the invitation email.)

![The Add menu on the Event Team page — Invite User and Add From…](/images/kb/event-team-add-menu.png)

Complete the required fields — **Email**, **First Name**, **Last Name** — and choose **What type of user is this?**. The choices are the default roles plus any custom roles you have created for this event. **Portal User** is not offered here: portal access is granted from Contacts, not by inviting someone to the team.

![The Invite User panel — email, name, the role picker and tags](/images/kb/event-team-invite.png)

<Tip>
**Tags** on a team member are used when assigning reviewers to an evaluation plan. See [set up an evaluation plan](/evaluations/setting-up-round-based-evaluations).
</Tip>

Select **Invite User** to create the account and send the invitation email.

### Roles with a session filter

If the role is **Session Manager**, **Evaluator Session Manager**, or a custom role that has session filters turned on, the button reads **Next** instead and a second step, **Set Session Filters**, asks which sessions the person is responsible for. The filter is required for these roles; **Invite User** stays disabled until at least one row has a value.

![The Set Session Filters step — a filter row, Add filter row, and the count of sessions that match](/images/kb/event-team-invite-filter.png)

A filter can use **Status**, **Formats**, **Tracks**, **Levels**, **Languages**, **Tags**, any custom dropdown session field, or **Source**. **Source** limits the team member to sessions by where they came from — the submission form they were submitted through, or **Manual** for sessions added by hand or imported without a form. Pick several values on one row to match any of them; add rows with **Add filter row** to require all of them. The preview under the filter counts how many sessions match. The team member then sees only those sessions and the speakers on them.

### Manage existing users

The **⋯** menu at the end of each row holds the actions for that team member:

![The row menu for a team member — Edit, Impersonate, Remove from event](/images/kb/event-team-row-actions.png)

- **Edit** — change the person's name, role, tags, or session filter. Changing your own role to one with fewer permissions shows a warning first, because you may lose the ability to manage the team.
- **Copy invite URL** and **Resend invite** — shown only while the person has never logged in. The URL is unique to that invitation; resending sends the same invitation email again.
- **Impersonate** — open the event as that person to check what their role shows. It needs the **Impersonate User** permission and is not available for portal users.
- **Remove from event** — takes away their access to this event only. Their account, and their access to other events, stays.
- **Unlock account** — appears after five wrong passwords lock an account. Unlocking also emails the person a link to reset their password.

Use the search box above the table to find someone by name or email, and **⋯ > Import** or **Export** next to **Add** to bring in or download the team list ([importing data](/settings/importing-data)).

## Default roles

Open the **Permissions** tab to see what each role can do. Roles are listed on the left — **Default Roles** first, then **Custom Roles** — and the grid on the right shows every permission for the selected role, grouped by module with a count such as **Sessions 3/6**.

![The Permissions tab with Session Manager selected — the default roles down the left, the permission grid on the right](/images/kb/event-team-permissions.png)

<Note>
- Default roles cannot be edited or deleted. Duplicate one if you need a variation.
- **Portal User** is the role every contact holds automatically once they have portal access. It never appears in the invite list.
</Note>

## Custom roles

### Create custom roles

If none of the default roles fit, select **Create new role** under the custom roles list, give it a **Role Name** and an optional **Description**, and select **Create**. The new role opens with every permission off; switch on what it needs, or use **All On** / **All Off** as a starting point. Changes save as you make them.

![The Create New Role dialog — Role Name and Description](/images/kb/event-team-create-role.png)

<Note>
- A custom role needs at least **Can view sessions** to use any Evaluation Plan permission other than **View Assigned Evaluations**.
- When Portal Tasks are enabled, team members receive automated emails when new file request messages arrive.
</Note>

Under **Evaluation Plans**, **Can promote sessions** controls who may promote submissions to the next round of a funnel evaluation plan — from **Sessions → Submissions**, the session profile, or the plan's **Rounds** tab. Admin and Admin Lite have it; Session Manager and Evaluator Session Manager do not, so duplicate one of those roles and turn it on to hand promotion to a session manager. Without it, **Promote** is disabled with a tooltip naming the permission. Demoting and moving back a round are not gated by it. A team member with a session filter can only promote sessions inside their filter.

### Duplicate, edit and delete roles

Hover over a role in the left-hand list and select the **⋮** menu next to its name. Default roles offer **Duplicate** only; custom roles also offer **Edit** and **Delete**.

![The role menu for a custom role — Edit, Duplicate, Delete](/images/kb/event-team-role-menu.png)

- **Duplicate** creates a new custom role with the same permissions, which is usually the fastest way to build one — a Session Manager who can also export, for example. A copy of **Session Manager** or **Evaluator Session Manager** keeps the session filter step when you invite people into it.
- **Edit** changes the role's name and description. Its permissions, fields and statuses are edited directly on the tabs.
- **Delete** opens **Delete Role**, which asks for a **Replacement Role** for every team member currently assigned to it before the role is removed.

Creating, renaming, deleting and editing an event's custom roles takes the event-level **Manage permissions** permission (Admin User has it). It does not depend on the person's organization role, so an event admin whose organization role is Program Manager can still manage the roles of their own event. Roles created under **Organization Settings → Team → Permissions** are managed by organization admins only.

## Field permissions (who can see or edit each field)

Use field-level permissions to limit sensitive data and keep teammates focused only on what they need.

Where: Event Team → Permissions → Role → Fields

![The Fields tab for a custom role — Contact Fields filtered to Phone, with both phone fields hidden](/images/kb/event-team-fields.png)

**How to configure**

1. Select the role, open **Fields**, and pick **Contact Fields**, **Session Fields** or **Group Fields**. Use the search bar to find a field, or scroll the list.
2. Set access per field:
   - View (Default) – user can see the field, but cannot change it.
   - Lock – user can see, but cannot update the field. Locking the session **Speakers** field also locks the session's participants: the role can see who is on a session but cannot add, remove, or reorder speakers, chairpersons, moderators, sponsors, or exhibitors. A lock holds everywhere the role can edit, not only on the record: locked fields are read-only in the Sessions and Submissions lists, are not offered in **Bulk Edit**, and a locked **Starts At** or **Ends At** also stops the role from dragging the session on the agenda.
   - Hide – field is hidden for this role in UI.

3. Use **Bulk Actions** — **Visibility** and **Lock Status** — to set a whole list at once.
4. Repeat for the other field tabs as needed. Changes are saved automatically.

**Tips & best practices**

- Start from a copy of a similar role or custom roles, then adjust field access to fine-tune access for vendors, volunteers, or reviewers.
- Hide Personal Identifiable Information (e.g., phone, compensation) from roles that don’t need it.
- Admin roles automatically retain full visibility and edit rights.

## Limit which statuses a role can set

Use the **Statuses** tab to control which session statuses people in a role can move a session into — for example, let track chairs send sessions to an accept queue but leave the final **Accepted** and **Declined** decisions to you.

Where: Event Team → Permissions → Role → Statuses

![The Statuses tab for a custom role, with Limit which statuses this role can set turned on and some statuses switched off](/images/kb/role-statuses-tab.png)

1. Select a custom role. Default roles are read-only here, as on the other tabs — duplicate one to restrict it.
2. Turn on **Limit which statuses this role can set**. Every status, including your custom statuses, starts switched on, so nothing changes until you switch one off.
3. Switch off each status the role should not set. Changes save automatically.

Turn **Limit which statuses this role can set** off again to let the role set any status.

### Only from certain statuses

Limiting the statuses a role can set says where a session may go *to*. You can also say where it may come *from* — for example, a Marketing Manager may mark a session **Accepted** only while it is still **Pending**, so a session you have already **Declined** stays declined.

Next to each allowed status is a **From any status** picker. Open it and tick the statuses the session must currently be in for this role to set the target; the picker then reads **Only from Pending** (or whichever statuses you ticked). Leave every box unchecked, or choose **Allow from any status**, to remove the condition. Changes save automatically. A condition only exists on a status the role is allowed to set, and it applies to changing an existing session — a new session can always start as **Pending**.

![The Statuses tab with the picker for Accepted open, titled "Set Accepted only when the session is currently…", Pending ticked and the summary reading Only from Pending](/images/kb/role-statuses-from-picker.png)

What people in a limited role see:

- **Status pickers only offer allowed statuses** — on the session profile, in the Sessions and Submissions tables, in bulk edit, and when adding a session. A session's current status still shows even if the role cannot set it. A status with a from-status condition is offered only while the session is in one of the statuses you listed.
- **They still see every session and every status.** The limit only covers moving a session *into* a status; saving a session without changing its status is always allowed, and new sessions can always start as **Pending**.
- **Refused changes name the status.** If a change reaches Sessionboard another way — an import, a bulk update, Team Lead, or the public API — it is refused with a message naming the status, for example *Your role is not allowed to set the session status "Accepted"*, or for a from-status condition *Your role can only change sessions to Accepted when they are currently Pending*. In an import or bulk update, only that row fails; the rest go through.

The event **Admin User** role and organization Admins can always set any status, and changes Sessionboard makes itself (such as integration syncs) are not limited.

## Apply roles to many events at once

To copy custom roles, field settings, or team role assignments from one event to many others in your organization, use **Org Settings > Bulk Permissions**. See [bulk-apply permissions across events](/event-team/bulk-apply-permissions-across-events).

## Common questions

<AccordionGroup>

<Accordion title="Which role should each teammate get?">

Start from the default roles and read their permission grids on the **Permissions** page before creating anything custom. Give full event control to admins; give people who run part of the program a **Session Manager** or **Evaluator Session Manager** role with a **filter** (by track, format, status, tag, custom dropdown, or the form a session came from) so they see only their sessions and speakers; give reviewers no more than **View Assigned Evaluations** and view on Sessions. Organization-level team members are all Admin Users ([inviting organization team members](/speaker-crm/inviting-organization-team-members)); use event-level roles for anything finer.

</Accordion>

<Accordion title="Can we restrict what a role sees or edits — specific fields, forms, or actions?">

Yes, in three layers. A **custom role** ([create custom roles](#create-custom-roles)) sets view, create, edit, and delete per module and per action, including who may promote sessions between evaluation rounds. **Field permissions** ([who can see or edit each field](#field-permissions-who-can-see-or-edit-each-field)) then set each session and group field to view, lock, or hide for that role, which is how you keep compensation, phone numbers, or internal notes away from volunteers and reviewers. **Status permissions** ([limit which statuses a role can set](#limit-which-statuses-a-role-can-set)) decide which session statuses the role can move a session into. Admin roles always keep full access.

</Accordion>

<Accordion title="What can evaluators, track chairs, and reviewers see?">

Only what their role and assignments allow. An evaluator sees the submissions assigned to them in their review portal, with the fields the plan makes visible ([reviewer view configuration](/evaluations/setting-up-round-based-evaluations#reviewer-view-configuration)). A track chair who must also accept or decline needs a Session Manager–type role with a filter on their track, or a custom role with edit on Sessions. The side-by-side comparison is in [what access do evaluators have?](/faq/will-evaluators-have-the-same-access-to-my-event-that-i-do-as-an-admin).

</Accordion>

<Accordion title="How is team access different from portal access?">

Team members are invited from **Event Team** and log into the admin app with a role. Speakers, sponsors, and exhibitors are **contacts and groups** who use the portal; they hold the **Portal User** role automatically and never see the admin app. To give a speaker admin access, invite them as a team member as well. Portal access itself is granted from Contacts ([grant portal access to a contact](/faq/how-to-grant-portal-access-to-an-event-contact)).

</Accordion>

<Accordion title="Someone cannot log in or never received the invite">

Use **Copy invite URL** or **Resend invite** from the team member's row menu if they have not logged in yet, and **Unlock account** after five wrong passwords. Share [new user login instructions](/event-team/new-user-login) and [reset password](/event-team/reset-password-user-instructions) with them. If your organization uses [single sign-on](/integrations/sso), they sign in through your identity provider instead.

</Accordion>

<Accordion title="Does access carry across events?">

Event roles are per event: invite the person to each event they work on, or add them at the organization level if they should reach every event as an Admin User. [Cloning an event](/faq/clone-an-event) copies the event team (all non-portal users) along with the structure and settings. To bring roles, field settings, or role assignments in line across events that already exist, use [Bulk Permissions](/event-team/bulk-apply-permissions-across-events).

</Accordion>

</AccordionGroup>
