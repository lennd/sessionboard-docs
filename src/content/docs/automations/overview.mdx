Automations watch a field on a session or a person — or watch for new form submissions. When that happens, Sessionboard enrolls the record and runs the action you set — send an email to the people on that record, assign reviewers to the session, or write a field's value into another language.

Open **Automations** from the event sidebar. Anyone on the event team can open it and build recipes; each event has its own list. The directory shows each recipe with what it watches, whether it is **Enabled** or **Disabled**, and when it last ran.

![The Automations directory with one Disabled recipe, its When line and Never run](/images/kb/automations-directory.png)

## How it works

Each automation is a short recipe: **When** something changes, **Then** do this.

| Piece | What you choose |
| --- | --- |
| **Object** | **Sessions** or **People**. A session change enrolls that session. A person change enrolls that contact. |
| **When** | Which field changed, optionally to which values, and any extra filters — or, for sessions, a **new form submission**. |
| **Then** | **Send email**, **Assign reviewers**, **Update language value**, or any combination. |
| **Re-enroll** | Every matching change, or only the first time for that record. |

The email goes to the enrolled record — not a blast list. A people automation emails that contact. A session automation emails that session's participants (speakers, moderators, and chairs), the submitter, or both — you choose with **Send to** on the email action.

Assign reviewers is for sessions. It places the enrolled session onto the evaluation plan rounds you pick and assigns the evaluators you choose.

## Create an automation

<Steps>

<Step title="Add one">

Open **Automations** and click **Add**. The empty state also has **Create automation**.

</Step>

<Step title="Start from the gallery or from scratch">

**Gallery** recipes fill in a When and leave you to finish the action:

- **Session accepted** — email speakers the first time status becomes Accepted.
- **Session declined** — email speakers the first time a session is declined.
- **Email session participants** — email speakers, moderators, and chairs when a field changes.
- **New submission received** — email the submitter or the session's participants when a submission form is completed.
- **Assign reviewers** — drop a session onto evaluation rounds when a field changes.
- **Email a person** — email that contact when one of their fields changes.

**From scratch** opens an empty When card for **Sessions** or **People**. You pick the field, then add an action.

![The Create an automation dialog on its Gallery tab, with the six recipes](/images/kb/automations-create-dialog.png)

New automations are **Disabled** until you attach an action and flip **Enable**.

</Step>

<Step title="Name it and save">

The name at the top of the builder is what appears in the list. Click **Save**. The header shows **Saving**, then **Saved**, or **Unsaved** while you still have edits. The rail on the left is the recipe in three parts — **Trigger**, **Then** and **Activity** — and the canvas reads top to bottom: the When card, then the actions, with **+** to add one.

## When

The **When** inspector is the trigger.

**Trigger** (sessions only). Session automations choose between two triggers:

- **A field changes** — fires when a session field updates. This is the default, and the only trigger for People automations.
- **Submission Form: New Submission** — fires when a form submission is completed. Drafts fire when they're finalized, not when they're saved. Pick a specific **Submission form**, or leave it on **Any submission form** to fire for every new submission in this event.

A submission happens exactly once per session, so this trigger always runs once per submission regardless of the re-enroll setting — a redelivered or edited submission won't send the email again.

**Field.** Pick the session or person field to watch — Status, Track, a custom dropdown, a date, and so on. Leave the field empty to enroll on any field change for that object.

**Who made the change does not matter.** A field-change automation fires however the value changed: an admin editing the record, a speaker or attendee editing their own profile in a portal, a form submission, an import, a Public API update, or an integration writing back — for example the Visit registration ID landing on a contact after a successful Visit registration. The first value ever written to an empty field counts as a change. The one exception is an automation's own actions, which never re-trigger the automation that ran them.

**Changed to any of these values.** Optional. For Status and other lists, this is the same picker as [embeds](/sessions/embeds) and evaluation plan filters: search, color dots in the admin order, and checkboxes so you can match more than one value (Accepted or Pending). Dates use a date picker. Text fields use a text box. Leave this off to enroll on every change to the field, regardless of the new value.

**Only enroll when.** Extra filters on the same record, again using the Embeds and Evaluation plans filter builder. Leave the list empty to enroll every matching field change. Click **Add filter** for another condition.

**Re-enroll.**

- **Every time this happens** — runs again on each matching change. Rapid edits within 45 seconds are grouped so the action fires once.
- **Only the first time** — one run per record. Use this for one-shot mail such as an acceptance email.

If the only action is assign reviewers, you can also check **Enroll records that already match when this turns on**. That assigns reviewers on up to 500 sessions that already match, without waiting for a new edit. Automations that send email do not offer this, so turning the recipe on cannot send that email to hundreds of existing records at once.

## Then

You need at least one action before you can enable the automation.

### Send email

Open **Send email** and choose how to build the message:

- **Compose new** — write the subject and body here, with merge tags.
- **Start from a template** — copy an event email template, then edit.
- **Reuse an existing campaign** — attach a [Send](/communications/email-campaigns) campaign as-is. Subject, body, and sender stay in Send.

The enrolled record is the recipient. Use **Send test** on this sheet to preview the message in your inbox without creating a live send.

**Send to** (sessions only). Session automations use the same recipient list as Send on the Sessions list, and you can pick more than one. **Select individual contacts** is not offered here, because an automation has no one sitting there to pick names.

- **Everyone** — submitters and participants.
- **All participants** — speakers, moderators, chairs, and other participant roles.
- **One role** — speakers, primary speakers, chairpersons, moderators, or a custom participant role on the event.
- **Session submitters** — the contact who submitted the form.

When you pick more than one recipient choice, they are combined: everyone in any selected group gets the email, and someone who matches more than one — a submitter who is also a speaker, say — still receives it once. **Primary speakers** emails only speakers flagged primary. An automation saved before this list existed keeps its previous recipients — all participants, the submitter, or both — until you change **Send to**.

**Session submitters** pairs naturally with the **Submission Form: New Submission** trigger — for example, an instant "we received your submission" email to the submitter.

### Assign reviewers

Open **Assign reviewers**. Choose the **Plan rounds** (plan name · round name), then the **Evaluators** — people already enrolled on a plan, or reviewer tags.

This uses the evaluation plan rounds already on the event. If you have not created rounds yet, set those up first — see [Round-based evaluations](/evaluations/setting-up-round-based-evaluations).

Reviewer assignment that you configure on the evaluation plan itself still lives under **Sessions → Evaluation**. Event **Automations** is the separate sidebar list for field-change recipes.

### Update language value

For events with [language variants](/settings/language-translation-variant) turned on. When the record enrolls, this action reads one field in one language and writes it into a field in another language on the same record — for example, a German-only submission's **Description (German)** into **Description (English)**, or the other way round. It works for Sessions and People automations.

Open **Update language value** and choose:

- **Copy from** — the field and its language. **(default)** is the event's default language.
- **Write to** — the field and the language to write. Only languages enabled on the event are listed. It can be the same field in another language, or a different field.
- **How** — **Translate** translates the text into the target language. **Copy as-is** copies it word for word.
- **If the target already has a value** — **Leave it (only fill empty values)**, the default, or **Replace it**.

Click **Save action**. Text, paragraph and rich-text fields are supported, including a session's **Title** and **Description**. A rich-text value that only contains an empty paragraph counts as empty. When a rich-text source goes into a plain-text field, the formatting is dropped.

The record's **Activity** shows each run as translated, copied, or skipped with the reason — **Source value is empty**, or **Target already has a value**. The action's own writes never trigger an automation, so it cannot loop.

<Note>
**Update language value** is greyed out when the event has no language variants. Hover the info icon for the reason, then turn on languages in **Event Details** — see [Language variants and translations](/settings/language-translation-variant).
</Note>

## Test, save, and enable

Save often. **Enable** is the switch that lets the recipe run on real field changes. Sessionboard asks you to add an action before it will turn on.

**Test** on the builder, or **Test against a session** / **Test against a person** on the **Activity** inspector, runs the recipe now.

- Leave the record picker empty to fire a synthetic run with no real record.
- Pick a real session or person to run the actions for that record.

<Warning>
A test with a record selected runs the live email action for that record's recipients. Use **Send test** on the email sheet when you only want a preview in your own inbox.
</Warning>

## Activity

The directory lists each automation as **Enabled** or **Disabled**, with a last-run line: **Never run**, **Last ran**, **Didn't run**, **Failed**, or **Running now**.

Open an automation and choose **Activity** for the run log — what fired, how long it took, and why anything was skipped or failed. Failed or partial runs can **Rerun** after you fix the action.

## Delivery history

**Activity** answers "what did this automation do?". **Delivery history** answers the question you get asked after the fact: "was this person emailed, and by what?"

Open **Automations** and choose the **Delivery history** tab. It lists every record any automation on this event has enrolled, newest first, 25 to a page.

![The Delivery history tab on the Automations directory](/images/kb/automations-delivery-history.png)

A line at the top counts how many records have been sent an automation email on this event, and — when it applies — how many of those were emailed by automations that have since been deleted.

Each row shows:

- **The record** — the session or person that was enrolled.
- **Emailed**, or the run's status when no email went out. An **Email sent** row is backed by the sent email itself, so it is evidence rather than an assumption. A completed run of an email automation that recorded no send reads **No email recorded** instead of claiming a delivery.
- **Skipped — &lt;reason>** where a record was enrolled but the action did not run.
- **Automation deleted**, on records handled by an automation that no longer exists, with the date it was deleted.
- When the record was enrolled, and when the run finished.

Two checkboxes narrow the list:

- **Emails only** — hide enrollments that sent no email.
- **Deleted automations only** — show only records handled by automations that have since been deleted.

<Note>
Deleting an automation does not delete its delivery history. That is the point of this tab: someone who received an automation email can still be traced back to the recipe that sent it after the recipe is gone.
</Note>

## FAQ

<AccordionGroup>

<Accordion title="Is this the same as automated emails?">

No. [Automated emails](/communications/automated-emails) are the system messages Sessionboard already sends — submission confirmation, portal invites, and the like. Automations are recipes you build: when a field you choose changes, send a message you write (or assign reviewers).

</Accordion>

<Accordion title="Is this the same as Email Campaigns?">

[Email Campaigns](/communications/email-campaigns) send to a segment you pick in Send. An automation email always goes to the enrolled record — that person, or that session's participants — even if you reuse a Send campaign for the content.

</Accordion>

<Accordion title="Where do evaluation-plan automations live?">

Under **Sessions → Evaluation**. Those recipes belong to evaluation plans. Event **Automations** is the list in the event sidebar for field-change emails and reviewer assignment.

</Accordion>

</AccordionGroup>
